# okf-parser 0.42.6

- links a prebuilt DuckDB instead of compiling its C++ amalgamation from
  source on every wheel build (#154). `libduckdb-sys` already knows how to
  download a prebuilt library from `duckdb/duckdb`'s own releases via
  `DUCKDB_DOWNLOAD_LIB=1`, but that code path was unreachable: the check
  lives entirely inside the non-`bundled` branch of its build script, and
  `rust-core/Cargo.toml` enabled `bundled` unconditionally. `duckdb` now
  carries `default-features = false` behind a package-level
  `bundled-duckdb` feature that stays on by default, so a plain
  `cargo build` still compiles from source; only the CI wheel jobs opt out.
  Wheel build time drops from 14-19 minutes per platform to 2-4;
- fixes the packaged executable failing to find its interpreter once the
  DuckDB link became dynamic. maturin responds to an external dynamic
  library by vendoring it into `okf_parser.libs/` and relocating the real
  binary to `okf_parser.scripts/`, several directories below the
  environment root. `python_cli()` looked for an interpreter only as a
  direct sibling of the executable, which held while it lived in the
  environment's own scripts directory but not after the move — it fell
  through to the system `python3`, which cannot import `okf_parser`. The
  search now walks every ancestor directory looking for `bin/python` or
  `Scripts\python.exe`, covering both layouts.
