# okf-parser 0.42.7

- takes DuckDB out of the packaged Rust executable's link graph entirely,
  and fixes the macOS and Windows wheels 0.42.6 published broken. Those
  wheels linked a `libduckdb` they did not ship, so the command failed at
  startup with a loader error. Only the Linux wheel worked, because
  `auditwheel` runs inside the manylinux container and vendored the library
  there; nothing equivalent runs for macOS or Windows;
- the underlying duplication is what made that possible. The Python
  distribution already depends on `duckdb`, and `okf-parser duckdb` exports
  through it via Ibis. The executable's own DuckDB served only the private
  `__engine-duckdb` subcommand, which nothing calls: `rust_core.py` uses
  `__engine-load` and `__engine-facts`, and no other caller exists. That
  second copy is what forced either a C++ amalgamation build in every wheel
  job or a dynamic library needing per-platform vendoring and rpath work;
- `duckdb` is now an optional Rust dependency behind a `duckdb-export`
  feature that is off by default, with `database.rs` and `__engine-duckdb`
  gated on it. The five wheels build without it. `okf-parser duckdb`
  continues to work unchanged, through Python;
- `scripts/check_no_duckdb_link.py` runs in every wheel job and fails the
  build if the executable names a DuckDB library or a wheel ships one. It
  reads the binary's own import names, so it holds for cross-built wheels
  with no host able to run them. Verified against the broken 0.42.6
  artifacts: it rejects all three failure shapes.
