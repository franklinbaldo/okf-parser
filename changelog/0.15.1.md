# okf-parser 0.15.1

## RFC 0006: declared column types via DuckDB DDL

Proposes (status: `proposed`) an optional `.schema.sql` declaration beside a
type's existing specification document (PR #33, superseding the JSON Schema
draft in #31): declaring a type's physical column types and catalog
comments — opt-in, per type, additive to RFC 0005's `VARCHAR`-everything
compilation.

**Trust model: `.schema.sql` is trusted DuckDB SQL, not a sandboxed data
format.** The whole script — CTAS, joins, `read_csv`/`read_json`, macros,
temp tables, anything a dedicated DuckDB connection accepts — is executed
as-is, in one connection. Nothing inspects its shape or statement types.
Only the *post-condition* is checked afterward against that connection's
own catalog: exactly one non-temporary table must exist, named for the
concept type. Every other table the script created along the way (a
staging table, a join source) is ignored. Running a bundle's `.schema.sql`
therefore grants it the same privileges as the `okf-parser` process itself
— treat it like a Makefile or a migration script, not a JSON Schema
document: don't run it against a bundle you wouldn't otherwise trust to
execute arbitrary code. (An earlier draft tried to make the file a
restricted, sandboxed subset of DDL instead — rejected; see the RFC's
"Alternatives considered.")

Implemented so far (`schema_export.py`, `declared_schema.py`):

- `schema --spec-template TEMPLATE` reads each type's `.schema.sql` (when
  present) and types that type's columns accordingly in JSON Schema/Zod
  output;
- a declared kind is looked up **scoped to `(concept_type, field)`**, never
  as one global `field=kind` table — a `.schema.sql` for `Fatura` declaring
  `valor` as `DECIMAL` never affects an unrelated `Pesquisa.valor` field
  just because the two types share a field name;
- a declared column whose observed data doesn't uniformly fit the declared
  kind is advisory: that field falls back to inference/`string`, and export
  never raises for it (unlike an explicit `--cast`, which stays strict and
  takes precedence within its type when both apply);
- `init --spec-template TEMPLATE [--write]` scaffolds a minimal spec
  document for every type missing one; `--infer-schema` additionally
  proposes a starter `.schema.sql`, with every column's type inferred by
  asking DuckDB's own `TRY_CAST` (`infer_kinds_via_duckdb`) rather than a
  regex, in one vectorized pass per type;
- `import SOURCE PATH --type NAME` materializes any DuckDB-readable source
  (CSV, Parquet, (ND)JSON) as one concept document per row — a separate,
  unrelated command that happened to land in the same change.

**Not yet implemented, still open RFC decisions** (the RFC states them as
design, but no code path builds them yet — do not read the RFC text as a
description of current behavior for these):

- whether a declared column that partially diverges degrades as a whole
  column (current RFC text) or row-by-row via a generated-column
  `TRY_CAST` over a preserved raw column (a live open question, since the
  raw/generated split already exists for other reasons);
- `apply`/`duckdb` compiling declared types at all — today only `schema`
  reads `.schema.sql`;
- `--fail-on-spec-divergence`;
- separating "declared," "effective," and "observed" schema exports, and
  the exact `DECIMAL`/`TIMESTAMP`/`TIMESTAMPTZ` export mapping for JSON
  Schema and Zod — flagged as needing a physical-type representation
  richer than the current closed `CastKind` vocabulary, deliberately
  deferred to its own round rather than decided under this change.
