# okf-parser 0.15.1

## RFC 0006: spec-driven relational typing and bidirectional spec sync

Proposes an optional second compilation input for RFC 0005's `apply`: a
type's specification, a sibling pair `<name>.md` + `<name>.schema.json`,
lets its declared field types and documentation compile into real DuckDB
column types and `COMMENT ON TABLE`/`COMMENT ON COLUMN` metadata, instead
of every column defaulting to `VARCHAR` with no documentation.

- the specification's structural contract is a real **JSON Schema Draft
  2020-12** document, not a bundle-invented schema language — a
  deliberately small v1 profile (`type`, `properties`, `required`,
  `description`, `format: date|date-time`, `items`, `x-okf-duckdb-type`) is
  interpreted by the compiler; every other keyword is preserved losslessly
  and exported as declared, never acted on or rejected;
- `properties.type.const` is the schema's only identity — no separate
  `defines:` field — compared to a concept's `type` the same exact-string
  way RFC 0005 compares an `--sql` `UPDATE` target;
- `--require-spec`'s already-shipped template contract is unchanged: it
  still resolves and checks for exactly one `.md` path; the schema file is
  referenced from that document's frontmatter (`schema: ./name.schema.json`),
  and only those two exact files are reserved bundle metadata, never an
  entire `.okf/specs/**` tree;
- divergence from the schema — a missing required key, a value that
  doesn't cast to its declared type — is always advisory, never a block on
  `check` or `apply`; `required` never produces a DuckDB `NOT NULL`
  constraint;
- **`ALTER TABLE` writes back to the schema, when one exists** —
  `ADD`/`DROP`/`RENAME COLUMN` sync `properties` and `required`, through
  the same candidate-tree/hash-recheck/atomic-replace mechanism RFC 0005
  already uses for concept documents, widened to cover the schema file
  too. `COMMENT ON` is deliberately kept out of `--sql`'s grammar —
  descriptions change by editing the schema file directly;
- value writeback is scalar and incremental: strings, integers, booleans,
  dates, and (timezone-aware and naive) timestamps are writable; `number`,
  `DECIMAL`, arrays, and composite types materialize and cast correctly but
  fail explicitly, by name, on an `UPDATE` attempting to change their
  value — never a silent `NULL`, drop, or stringified fallback;
- a type with no specification compiles exactly as RFC 0005 already
  defines — nothing here is a new obligation on bundles that don't opt in.

Status `proposed`, and depends on RFC 0005, now accepted and implemented
(#30, #32), for the `ALTER TABLE` mechanism this RFC extends.
