# okf-parser 0.15.1

## RFC 0006: spec-driven relational typing and bidirectional spec sync

Proposes an optional second compilation input, shared normatively by
`apply`, the persistent `duckdb` command, and `schema`
(`schema_export.py`): a type's specification, a sibling pair `<name>.md` +
`<name>.schema.json`, lets its declared field types and documentation
compile into real DuckDB column types, `COMMENT ON TABLE`/`COMMENT ON
COLUMN` metadata, and canonical JSON Schema/Zod/Pydantic output, instead of
every column defaulting to `VARCHAR` with no documentation.

- the specification's structural contract is a real **JSON Schema Draft
  2020-12** document, not a bundle-invented schema language — a
  deliberately small v1 profile (`type`, `properties`, `required`,
  `description`, `format: date|date-time`, `items`, `x-okf-duckdb-type`) is
  interpreted by the compiler; every other keyword is **semantically
  preserved** and exported as declared, never acted on or rejected — not a
  byte-identical guarantee;
- `properties.type.const` is the schema's only identity — no separate
  `defines:` field — compared to a concept's `type` the same exact-string
  way RFC 0005 compares an `--sql` `UPDATE` target;
- **discovery is semantic and command-agnostic**: any document with
  `type: OKFTypeSpec` is classified as bundle metadata during the normal
  Markdown walk, independent of any template, so `apply`/`duckdb`/`schema`
  all find it the same way. `--require-spec`'s already-shipped,
  `check`-only template contract is untouched and gains no new role;
- divergence from the schema — a missing required key, a value that
  doesn't cast to its declared type — is always advisory, never a block on
  `check`, `apply`, `duckdb`, or `schema`; `required` never produces a
  DuckDB `NOT NULL` constraint;
- **`ALTER TABLE` writes back to the schema, when one exists** —
  `ADD`/`DROP`/`RENAME COLUMN` sync `properties` and `required`, through
  the same candidate-tree/hash-recheck/atomic-replace mechanism RFC 0005
  already uses for concept documents, widened to cover the schema file
  too. `COMMENT ON` is deliberately kept out of `--sql`'s grammar —
  descriptions change by editing the schema file directly;
- value writeback is scalar and incremental: strings, integers, booleans,
  dates, and (timezone-aware and naive, with a canonical RFC 3339
  serialization) timestamps are writable; `number`, `DECIMAL`, arrays, and
  composite types materialize and cast correctly but fail explicitly, by
  name, rather than a silent `NULL`, drop, or stringified fallback. The
  guard compares each row's final value against what the document
  originally authored, so it catches a new non-writable value from any
  source — `UPDATE`, `ADD COLUMN ... DEFAULT`, or a `DROP`+`ADD` reset —
  while leaving untouched values and pure renames alone;
- `duckdb` additively materializes one table per specification-having type
  into a dedicated `{schema}_types` schema, never touching the existing
  `concepts`/`links`/`reserved`/`diagnostics` four-table contract or any
  table it didn't create itself;
- `schema` (`schema_export.py`): a declared schema property wins over
  `--infer-types`/`--cast`; a conflicting `--cast` is reported, not
  silently overridden. JSON output gains a `diagnostics` key; Zod output
  keeps its bare-string stdout contract and reports advisory diagnostics
  via stderr with exit code unchanged;
- `x-okf-duckdb-type` is never spliced into DDL as raw text — validated by
  an isolated DuckDB parse before use, with the catalog-normalized type
  used thereafter;
- a type with no specification compiles exactly as RFC 0005, `duckdb`, and
  `schema` already define — nothing here is a new obligation on bundles
  that don't opt in.

Status `proposed`, and depends on RFC 0005, now accepted and implemented
(#30, #32), for the `ALTER TABLE` mechanism this RFC extends.
