# okf-parser 0.15.1

## RFC 0006: declared column types via DuckDB DDL

Proposes an optional `.schema.sql` declaration beside a type's existing
specification document (PR #33, superseding the JSON Schema draft in #31):
one `CREATE TABLE`, parsed by DuckDB itself, declaring a type's physical
column types and catalog comments — opt-in, per type, additive to RFC
0005's `VARCHAR`-everything compilation.

- the contract is DuckDB's own DDL rather than an invented schema
  language: no type-mapping table, no meta-schema validator dependency,
  no v1 keyword profile. A declaration whose shape or table name doesn't
  match RFC 0005 compilation exactly — advisory, never a block;
- a raw/typed split resolves what two earlier revisions of the cast rule
  couldn't: a hidden, compiler-owned raw column (`VARCHAR` for a scalar
  field, `VARCHAR[]` for an array) holds the document's text exactly as
  authored, and the declared column is a DuckDB `GENERATED ALWAYS AS`
  projection computed from it — never the only copy of the data, so a
  cast that rounds or truncates is never a silent loss;
- casting is all-or-nothing per column, gated by a lexical exactness
  predicate (checked against the raw text, not a numeric carrier) rather
  than by discarding a value after the fact — verified against concrete
  counterexamples a carrier-based rule missed twice, including a DuckDB
  `DATE` cast that truncates a date-time's literal text without
  timezone conversion;
- `apply`'s typed columns are read-only in v1 because a generated column
  already refuses assignment; the underlying raw column gets the same
  protection `apply` already gives its other internal columns;
- comments: the declaration is canonical and overwrites; an existing
  catalog comment the declaration doesn't specify is preserved and
  reported, never dropped;
- one `--fail-on-spec-divergence` flag across `check`/`apply`/`duckdb`/
  `schema` changes only the exit code — same diagnostics, same artifact,
  same streams;
- `schema` exports the declared type as stated intent even when the data
  currently diverges, with the divergence carried as diagnostics rather
  than silently widening the exported shape;
- writeback — both into the declaration file and of typed values through
  `apply` — is deferred whole to a future RFC 0007, since both need a
  canonical per-type serialization this RFC doesn't have to solve to make
  declared types useful for reading.

Status is `proposed`. Four rounds of PR review progressively found and
closed: a `:memory:` connection is not itself a sandbox against a
declaration's own `CREATE TABLE ... AS`; `TRY_CAST` alone is not
lossless, and neither is a fixed-width numeric carrier, which just moves
the same failure mode to a different edge case (resolved by the
raw/generated-column split); a schema-level `apply` write guard doesn't
see a value change behind a stable column type; a `{schema}_types`
ownership marker is forgeable, resolved by reusing the per-table
collision check `duckdb.py` already has for its four contract tables
instead of inventing a new mechanism, with automatic deletion dropped
from v1 entirely; and, most recently, that a compiled raw column was
protected by name but not by write-guard, that array fields need a raw
`VARCHAR[]` not `VARCHAR`, and that a `DATE` exactness predicate needed
deriving against DuckDB's actual (textual, not timezone-aware) cast
behavior rather than by reasoning about what "midnight" should mean.
