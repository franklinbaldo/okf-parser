# okf-parser 0.14.2

## RFC 0005: relational writes to frontmatter fields

Proposes `okf-parser apply PATH --sql 'UPDATE "Rotina" SET ... WHERE ...'`,
responding to the direction `duckdb` and `schema` never opened: mutating
frontmatter in bulk instead of only reading it.

- the SQL table name **is** the exact authored `type` value, quoted — not a
  flag, not a derived slug. Two earlier drafts got this wrong: naming the
  table by the type's slug is broken because `type_slug()` isn't injective
  (this RFC's own `"Revisao Ciencia"` / `"Revisão Ciência"` example collides
  on one slug); a required `--type` flag with a fixed table name worked, but
  review pointed out DuckDB's quoted-Unicode-identifier support made the
  flag unnecessary duplication of what the SQL already states;
- `apply` materializes **every** concept type as its own table inside one
  in-memory DuckDB database and hands the caller's SQL to it mostly as-is —
  DuckDB's own parser and binder resolve the target identifier (Unicode,
  quoting, case folding), so `apply` no longer re-implements any of that.
  Which type was actually mutated is discovered from a before/after diff of
  every table, not declared up front;
- `--sql` accepts a bounded script rather than a single statement: zero or
  more leading `ALTER TABLE ADD/DROP/RENAME COLUMN` statements followed by
  exactly one trailing `UPDATE`, run as one DuckDB transaction. Introducing
  a field is `ADD COLUMN` (a plain `UPDATE` cannot bind to a column that
  doesn't exist — that's ordinary SQL, not something `apply` should paper
  over by synthesizing columns from the `SET` list, which an earlier draft
  did and review correctly rejected); removing a field bundle-wide is `DROP COLUMN`, distinct from the row-level `SET field = NULL`; renaming a field
  bundle-wide is `RENAME COLUMN`;
- one writable namespace per type (that type's authored frontmatter keys,
  exactly once) plus filesystem identity under a reserved `__okf_*` prefix,
  with an explicit guard against DuckDB's case-insensitive identifier rules
  for both columns and type names — the latter now falls out for free from
  DuckDB's own "table already exists" error when two types fold to one
  identifier;
- v1 scope is top-level scalar fields with lexical `VARCHAR` semantics;
  structured (list/map) fields and non-`VARCHAR` `ADD COLUMN`s are rejected
  by inspecting the script's *result*, not by parsing it beforehand — same
  posture for protecting `__okf_*` columns and catching a row-identity
  change, all checked after execution against an ephemeral in-memory
  database that has touched nothing real yet;
- dry-run by default, matching `format`; a document that cannot round-trip
  losslessly aborts the whole `--write` invocation, not just that file;
- writes back through a purpose-built round-trip YAML loader instead of
  reserializing frontmatter wholesale, so an untouched key, comment or blank
  line survives;
- validates the candidate bundle against the *original* bundle's own
  diagnostics and aborts only on newly introduced normative ones, so `apply`
  stays usable on a bundle a migration is meant to repair;
- re-checks every path considered during validation immediately before
  writing — content hash for touched files, size/mtime for the hardlinked
  rest, plus a directory listing diff for additions/deletions — and aborts
  if anything changed since `apply` validated it; each file replace is an
  atomic rename, not an in-place write;
- bounds its idempotency guarantee to what `apply` itself controls: no diff
  from its own machinery beyond what the caller's SQL output specifies —
  stated honestly now as *not* covering whether a script is safe to rerun at
  all. A converged type-rename's second run hits a "table does not exist"
  error rather than a graceful no-op, and a re-run `ADD COLUMN` hits
  "column already exists"; both are real DuckDB catalog errors `apply`
  surfaces as-is rather than smoothing over.

Status remains `proposed`. Five rounds of PR review (#30) progressively
found: the mechanism unimplementable as first drafted; presence/null
semantics, concurrency, and validation baseline undefined after the
per-type-table redesign; that naming the table by type slug broke type
selection, rename idempotency, and the `--field` sugar all at once; that a
`--type`-flag fix for that was itself unnecessary given DuckDB's Unicode
quoted identifiers; and finally that `apply` parsing SQL identifiers and
synthesizing columns at all was reimplementing what DuckDB's own parser,
binder, and catalog already do — replaced by materializing every type,
letting DuckDB run a bounded `ALTER TABLE`+`UPDATE` script, and validating
the result instead of the request. One design fork is still genuinely
open — whether a mutation that changes `type` itself is allowed at all —
and is what keeps this RFC at `proposed` rather than `accepted`. #26 stays
open until it resolves.
