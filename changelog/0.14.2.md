# okf-parser 0.14.2

## RFC 0005: relational writes to frontmatter fields

Proposes `okf-parser apply PATH --sql "UPDATE __okf_staging SET ... WHERE ..."`,
responding to the direction `duckdb` and `schema` never opened: mutating
frontmatter in bulk instead of only reading it.

- runs one parsed `UPDATE`, and nothing else, against a flattened temporary
  staging table (not a view — DuckDB cannot `UPDATE` a view) built from the
  concept relation, so plain `SET field = value` works without JSON-path
  expressions against `frontmatter_json`;
- one writable namespace (authored frontmatter keys, exactly once) plus
  filesystem identity under a reserved `__okf_*` prefix that cannot collide
  with an authored key;
- dry-run by default, matching `format`;
- writes back through a purpose-built round-trip YAML loader instead of
  reserializing frontmatter wholesale, so an untouched key, comment or blank
  line survives;
- refuses to target filesystem-derived columns (`__okf_path`,
  `__okf_concept_id`, `__okf_logical_key`);
- stages and validates the full candidate bundle with `check` *before* any
  real file is touched, and writes nothing if that fails — not a
  write-then-report sequence;
- bounds its idempotency guarantee to what `apply` itself controls: no diff
  from its own machinery beyond what the caller's SQL output specifies. It
  cannot make a non-deterministic `UPDATE` convergent, and no longer claims
  to.

Status remains `proposed`: PR review (#30) found the mechanism as first
drafted was not implementable (`UPDATE` against a view, colliding column
names) and one requirement contradicted #26 itself (validate-after-write).
This revision addresses those findings; #26 stays open until the RFC is
accepted.
