# okf-parser 0.14.2

## RFC 0005: relational writes to frontmatter fields

Proposes `okf-parser apply PATH --sql "UPDATE rotina SET ... WHERE ..."`,
responding to the direction `duckdb` and `schema` never opened: mutating
frontmatter in bulk instead of only reading it.

- models a bundle as **one table per concept type** (`rotina`,
  `revisao-ciencia`, ...), matching how `schema_contract.py` already compiles
  one contract per type, instead of one table spanning every type's fields;
- runs one parsed `UPDATE`, and nothing else, against a temporary table for
  the targeted type (not a view — DuckDB cannot `UPDATE` a view), so plain
  `SET field = value` works without JSON-path expressions against
  `frontmatter_json`, and a mutation scoped to one type never materializes
  the rest of the bundle;
- one writable namespace per type (that type's authored frontmatter keys,
  exactly once) plus filesystem identity under a reserved `__okf_*` prefix,
  with an explicit guard against DuckDB's case-insensitive identifier rules,
  not just the prefix;
- v1 scope is top-level scalar fields with lexical `VARCHAR` semantics and an
  explicit presence/null contract (`SET field = NULL` deletes the key);
  structured (list/map) fields are rejected as mutation targets rather than
  silently mistyped;
- dry-run by default, matching `format`; a document that cannot round-trip
  losslessly aborts the whole `--write` invocation, not just that file;
- writes back through a purpose-built round-trip YAML loader instead of
  reserializing frontmatter wholesale, so an untouched key, comment or blank
  line survives;
- validates the candidate bundle against the *original* bundle's own
  diagnostics and aborts only on newly introduced normative ones, so `apply`
  stays usable on a bundle a migration is meant to repair;
- re-hashes every touched file immediately before writing and aborts if it
  changed since `apply` read it, so a concurrent edit is never silently
  overwritten; each file replace is an atomic rename, not an in-place write;
- bounds its idempotency guarantee to what `apply` itself controls: no diff
  from its own machinery beyond what the caller's SQL output specifies. It
  cannot make a non-deterministic `UPDATE` convergent, and no longer claims
  to.

Status remains `proposed`. Two rounds of PR review (#30) found the mechanism
unimplementable as first drafted, then found the per-type-table redesign
still left presence/null semantics, concurrency, and validation baseline
undefined; this revision addresses those findings. One design fork is still
genuinely open — whether a mutation that changes `type` itself migrates a
document to its new type's table, or is refused — and is what keeps this RFC
at `proposed` rather than `accepted`. #26 stays open until it resolves.
