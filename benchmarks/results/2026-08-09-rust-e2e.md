# Rust end-to-end engine — 2026-08-09

Environment: Linux x86_64 workspace, warm filesystem cache, Python 3.12.13,
Node 24.14.0, Rust 1.97.1, release build, 32-reader window, one measured round.
The shared corpus has four linked Markdown paragraphs per small concept. Before
timing, each harness requires the complete native and Rust bundle outputs to be
equal.

| Adapter | Documents | Native load | Rust end-to-end | Speedup |
| --- | ---: | ---: | ---: | ---: |
| Python/Ibis | 10,000 | 5,004 ms | 626 ms | 7.98× |
| Python/Ibis | 100,000 | 49,712 ms | 7,711 ms | 6.45× |
| TypeScript | 10,000 | 1,736 ms | 248 ms | 6.98× |
| TypeScript | 100,000 | 17,698 ms | 2,603 ms | 6.80× |

The Python Rust time includes JSON decoding and construction of Ibis memtables;
the TypeScript time includes JSON decoding and camel-case adapter projection.

A second 100,000-file corpus measured the native executable directly. Files were
small (frontmatter, heading, and one unresolved link); timing includes discovery,
bounded reads, parsing, validation, link resolution, digests, and terminal output:

| Rust terminal | Time | Peak RSS |
| --- | ---: | ---: |
| JSON bundle (`load`) | 1,056 ms | 217 MiB |
| Embedded DuckDB (`duckdb`) | 1,557 ms | 259 MiB |

The TypeScript harness initially failed at 16,366 files because corpus creation
used unbounded `Promise.all(writeFile)`. The benchmark now creates files through
a bounded 32-operation window, matching the production backpressure contract.
These are same-host engineering measurements, not release thresholds.
